## 무엇이 문제였나

8월에 Supabase egress 초과를 잡았다. `_refresh_job_groups` 가 매 스크랩마다 전체 코퍼스를
다시 읽던 걸 끊었고, 다시 새지 않는지 보려고 `egress_meter.py` 를 넣어 런마다
`[EGRESS]` 줄과 `egress_mb` 컬럼을 남기게 했다. 그리고 또 넘었다 — 8.507 / 5 GB (170%).
유예가 9/12 에 끝나고 그 뒤로는 요청이 402 로 돌아온다. 공개 보드가 포폴로 라이브라
보드가 죽으면 안 된다.

이번엔 계측 로그가 있으니 범인이 바로 나올 줄 알았다.

## 장면 1 — 계측된 게 전부가 아니었다

- **앞에 있던 것**: `api.log` 에 `[EGRESS]` 줄 91개. `search_logs` / `phase1_run_logs` /
  `card_eval_run_logs` 에 `egress_mb` 컬럼.
- **기준**: `기준 없이 시작함`. 로그부터 열었다.
- **한 것**: `grep '\[EGRESS\]' api.log` 를 awk 로 합산. 세 run_log 테이블의 `egress_mb` 를
  빌링 시작일(8/16) 이후로 날짜별 집계.
- **본 것**: 8/16 이후 파이프라인 합계 **1,225 MB** — scrape 804 / phase1 372 / card-eval 49.
  scrape 는 평균 26 MB/회로 8월 수정 후 값을 유지하고 있었다.
  청구서는 8.51 GB. **계측된 게 전체의 14%.**
- **틀린 것**: 없음. 다만 이 시점에 "나머지는 브라우저"라고 바로 단정할 뻔했다.
  잔차는 측정이 아니라 뺄셈이다.

## 장면 2 — 프론트엔드 쿼리를 그대로 재현해서 쟀다

- **앞에 있던 것**: 잔여 86% 의 출처가 없다. `egress_meter` 는 httpx 훅이라
  파이썬 클라이언트만 센다. 브라우저가 PostgREST 를 직접 때리는 건 원리적으로 못 본다.
- **기준**: 추측하지 말고, 프론트엔드가 실제로 던지는 쿼리를 컬럼 목록까지 그대로 복제해
  curl 로 바이트를 잰다. 브라우저와 같게 `Accept-Encoding: gzip` 을 붙인다.
- **한 것**: anon 키로 `PublicBoard` 의 쿼리, service 키로 `Dashboard.tsx` 의
  `fetchJobs` / `fetchEvaluations` / `fetchFailJobIds` / sentence-index 청크를 각각 측정.
  `create_client` 를 쓰는 파이썬 파일 중 `egress_meter` 없는 것도 셌다.
- **본 것**:
  - `published_jobs` `select('*')` = 751행 **395 KB gzip**, 방문자 1명당. 페이지네이션 없음.
  - `fetchEvaluations` = 19,714행, 1000행 페이지가 651 KB gzip → 20페이지 **13.0 MB**.
  - 콜드 캐시 sentence-index **9.4 MB** (100행 청크가 348 KB).
  - 대시보드 1회 오픈 = 웜 **13.9 MB** / 콜드 **23.3 MB**.
  - `egress_meter.install` 이 있는 파일은 `app_db.py`, `job_evaluator.py` **둘뿐**.
    `create_client` 를 쌩으로 쓰면서 계측이 없는 파일이 82개. `daemon.py` 도 미계측 — 5초 폴링,
    응답 960 B (body 2 B + 헤더 958 B), 17,280회/일.
- **틀린 것**: `Dashboard.tsx:493` 주석을 믿었다. "keyword-fail 행이 테이블의 대부분이라
  걸러낸다" 고 쓰여 있어서 무거운 행은 이미 빠졌다고 생각했다. 세어보니
  `pb_stage_a_pass` = true **19,714** / false 17,146 / **null 0**.
  null 행 1000개 페이지가 2 바이트로 돌아왔다 — null 버킷은 비어 있다.
  필터가 거르는 건 절반이고, **남는 19,714행이 전부 무거운 JSON 행**이었다.
  주석은 쓰일 당시엔 맞았을 수 있지만 지금은 아니다.

## 장면 3 — 압축 여부가 결론을 3.4배 흔들었다

- **앞에 있던 것**: 계측치(1.23 GB)와 청구서(8.51 GB)를 비교하려면 단위가 같아야 한다.
  gzip 과 raw 가 3.4배 차이났다. Supabase 가 압축 후로 청구하면 파이프라인 몫이 14%,
  압축 전이면 ~44%. 후자면 이야기가 "엉뚱한 데를 고쳤다" 가 아니라
  "절반만 고쳤다" 가 된다.
- **기준**: 파이프라인 한 종류만 돈 날을 찾는다. 그날 청구액이 계측치 + 데몬 근처면
  압축 청구, 3.4배 근처면 비압축.
- **한 것**: run_log 집계에서 scrape 만 돌고 phase1/card-eval 은 0인 날 = **8/26**.
  Supabase 의 `usage/daily` 를 페이지 컨텍스트에서 호출 → **401**.
  세션 토큰을 꺼내 쓰는 대신, 차트가 이미 들고 있는 데이터를 recharts SVG 의
  React fiber `memoizedProps.data` 에서 읽었다.
- **본 것**: 8/26 계측 78.2 MB, 실제 **108.6 MB**. 비압축 청구였다면 파이프라인만으로
  78.2 × 3.4 ≈ 266 MB 여서 108.6 을 넘는다 → 불가능. **압축 청구 확정.**
  18일치 합계가 **8.507 GB** 로 청구서와 정확히 일치. 잔여 **7,281 MB (86%)**.
  `egress_rest` 가 사실상 100% (realtime 0.06~0.44 MB/일, auth 0.02).
  8/27: 실제 1,374.7, 파이프라인 151.2 → 잔여 1,223 MB ≈ 대시보드 50~85회 오픈.
  큰 막대가 뜬 날(16·18·19·21·27)은 전부 개발한 날이다.
  9/1 은 파이프라인 0 인데 11.6 MB — 데몬 폴링 바닥값.
- **틀린 것**: API 를 그냥 부르면 될 줄 알았다. 401 을 보고서야 대시보드가 별도
  베어러를 쓴다는 걸 알았다. 토큰을 꺼내는 쪽으로 가지 않고 DOM 으로 돌린 건
  결과적으로 맞았지만, 처음부터 "이미 렌더된 데이터가 있는데 왜 다시 부르나" 를
  생각했으면 한 번에 갔다.

## 남은 것

- **계측기는 "어디를 안 재는지"를 같이 적어야 한다.** `egress_meter` 독스트링에
  "LLM, Realtime, psycopg2 는 안 셈" 은 적혀 있었다. **브라우저가 빠져 있었다.**
  정작 그게 83% 였다. 안 세는 목록이 불완전하면 세는 숫자가 사람을 속인다.
- **잔차를 한 범인에게 몰지 마라.** 7.28 GB 는 뺄셈이지 측정이 아니다.
  브라우저 + 계측 없는 스크립트 82개 + Studio 가 다 그 안에 있다.
- **비용 단위를 모르면 비율 결론을 내지 마라.** 판별자는 단일 요인만 돈 날이다.
  그런 날을 만들어두는 것 자체가 관측 설계다.
- **코드 주석의 사실 주장에는 유통기한이 있다.** 세는 게 curl 한 번이면 센다.
- **비용 화면을 여는 것 자체가 비용이면 계측이 자기를 갉아먹는다.**
  `egress_mb` 를 보려고 `/admin` 을 열면 14 MB 다. 숫자만 볼 땐 `grep '\[EGRESS\]' api.log`.

수정은 아직 안 했다. 순서는 정해졌다 — 공개 보드를 정적 스냅샷으로 떼어내
9/12 를 방어하고(방문자당 395 KB → 0), `fetchEvaluations` 컬럼 분리(13 MB → ~1.5 MB),
`daemon.py` 폴링 5초 → 30초. 그리고 키워드를 좁히면 코퍼스가 줄어 이 셋이 동시에 작아진다.
